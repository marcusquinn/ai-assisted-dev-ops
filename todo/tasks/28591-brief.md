## What

Implement the first independently mergeable social-knowledge foundation:

1. Add a private SQLite corpus catalog under the existing personal knowledge base.
2. Register the existing personal `_knowledge` tree as the `personal:default` alias without moving user files.
3. Derive the local principal from an owner-only authentication-context file rather than a caller-provided principal or corpus ID.
4. Resolve only active corpora granted to that principal through active workspace membership and explicit capability grants.
5. Keep existing `off`, `repo`, and `personal` modes and existing add/list/search behavior compatible.

This phase does not add social objects, archive/API ingestion, federated retrieval,
team key distribution, or browser capture; those remain in later parent phases.

## Why

The current personal mode directly opens one global path. Later personal/team
federation needs a physical corpus boundary and a default-deny resolver before
any social data is collected. The transition must be additive: existing users
keep the same personal path and no automatic file move occurs.

### Implementation Steps

1. Add bounded CLI, catalog, and context modules implementing schema-v1 initialization with the parent catalog tables, private alias indirection, WAL, foreign keys, busy timeout, atomic transactions, and `0600` database/context files beneath `0700` private directories.
2. Bootstrap one opaque local principal, personal workspace, corpus, membership, and `knowledge.read|write|manage` grants; persist only the opaque principal ID in the authentication context.
3. Register `personal:default` with `location_ref=<personal-base>/_knowledge`; reject conflicting aliases or out-of-base locations.
4. Add list/resolve commands that derive the principal from the validated context file and require every active authorization edge before returning a path.
5. Wire personal provision/add/list/search to the helper while leaving repo mode untouched.
6. Add focused negative tests and run all existing knowledge compatibility suites.
7. Update the core contract with the additive layout and fail-closed rules.

### Hazards and Compatibility

- **Concurrency/atomicity:** Schema/bootstrap writes use WAL, busy timeout, foreign keys, and one `BEGIN IMMEDIATE` transaction; context creation uses write-fsync-replace semantics.
- **Migration/rollback:** The alias references the existing tree; no automatic move occurs. Schema bootstrap is additive and idempotent.
- **Mixed-version/backward compatibility:** Existing binaries ignore the new catalog and retain the legacy path; new binaries preserve `off|repo|personal` and the current personal location.
- **Idempotency/retry:** Repeated provisioning reuses the same principal/workspace/corpus and grants. A failed transaction cannot leave a partial authorization graph.
- **Partial failure/recovery:** Missing, symlinked, wrong-owner, group/world-readable, malformed, or unknown-principal context fails closed. A catalog failure does not mutate legacy content.

## Context & Decisions

- The local filesystem owner and a `0600` non-symlink context file form the Phase 1 authenticated context; Phase 6 may replace this with multi-human wrapped identities without changing resolver semantics.
- Catalog IDs and corpus-directory IDs are random opaque values. `personal:default` is a private logical alias, not a physical path component.
- Explicit capability grants are retained even for personal owner access so later workspace support does not require a permissive compatibility exception.
- Repo-mode knowledge remains outside the personal/workspace catalog in this phase.
- CLI, catalog, and context responsibilities are separate modules so each security boundary stays reviewable and the Qlty new-file complexity gate remains clean.
